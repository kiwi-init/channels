# 0.16.0 release checklist

Do not tag a bus branch. Tag main after `bus/release-0.16.0` lands.

## What changes for people and agents

- **Merge bus (#251):** agents push `bus/<task>`; the bus merges, tests the merged tree and lands it on main. Pull requests from people join with the `queue` label.
- **Agents:** the brief tells agents to write like teammates in a chat channel (#267). A restarted session on another model no longer takes a seat (#282). Grok's `kind` field and wrapped kiwi binaries are recognised by the hooks (#280).
- **kiwi sh:** thread files, review rounds and a read-only `query` command over the channel (#264).
- **Escalations:** an agent can hand a live browser tab to a person (#265).
- **App:** in coordinator mode a person's replies stay in the conversation (#267), pictures open in an annotator (#275), pasted images are compressed (T315), and the composer has dictation (T316).
- **Daemon protocol:** unchanged from 0.15.0.

## Order

1. Land `bus/release-0.16.0` (version 0.16.0, CHANGELOG, site download names, this checklist).
2. If more branches landed on main after this one, run `bun run changelog --write` on main, check the new entries' descriptions against what each PR finally did (the script takes each squash commit's first paragraph, which for a multi-commit PR is often another PR's text), and commit.
3. Rehearse the release on main's commit: `gh workflow run ci.yml --ref main`, then wait for `ci-ok`. Its `release / rehearsal` job runs the build a tag runs (`release-build.yml`) without publishing: the version and changelog checks, `bun test` and the builds on macOS, and the desktop app packaged and checked on macOS and Linux. Only this manual run signs and notarizes the macOS app (a pull request's rehearsal builds it unsigned), so it is the one that proves signing works; the Linux packages are never signed. Don't tag until it passes; it prints the tag to push.
4. Tag `v0.16.0` on main's commit and push the tag. The release workflow checks the version and the changelog, builds the CLI and the desktop app, and publishes the GitHub release. Wait until it has the CLI binaries, the dmgs, the zips, the AppImage and the deb.
5. Watch the `deploy-relay` job, which runs after `publish`. If it fails, the release still stands: fix the cause and re-run the job, or deploy by hand with `bun run relay:deploy`.
6. Update the CLI (`curl …/install | sh`) and the Kiwi app on each machine.
7. Start a new session for each agent. The new brief (#267) and the seat model check (#282) reach an agent only through a new session (Claude Code's SessionStart) or a new `kiwi join`; Kimi Code and Grok get the brief only from `kiwi join` or a pasted `kiwi prompt`.

## Do not

- Do not deploy the Worker by hand before the GitHub release exists: the site's download links name `Kiwi-0.16.0-…` and would 404.
- Do not tag a branch. If main has moved since this branch landed, rewrite the changelog on main (step 2), rehearse (step 3) and tag main.
